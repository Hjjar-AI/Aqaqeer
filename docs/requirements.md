## 1. Working agreement

Act as a senior Android engineer helping a beginner. Explain decisions simply. Use the defaults below; ask only when a missing answer materially changes scope, security, destructive behavior, or architecture. Do not repeatedly ask about settled requirements.

Continue authorized milestones in bounded steps. Report changes, checks actually run, limitations, and how to run the app. Never invent test, device, signing, or commit results; do not create a repository just for reporting.

**Confirmed publishing model:** admins coordinate so only one publishes at a time. Keep Telegram-only v1. Publishing is best effort, with no guaranteed distributed lock or atomic conditional write. Reconnection may automatically resume queued publishing; if another admin is publishing, admins must coordinate to avoid overlap. Do not claim guaranteed concurrent writes.

## 2. Product and scope

Android app for one pharmacy per phone, fewer than 100 medications and approximately 60 trusted users. Shows medication availability by section. V1 has an Arabic-only interface with full RTL; English medication names and other specified English data fields remain supported with correct bidi handling. No interface language selector or English interface is included in v1. Information only; no patients, prescribing, quantities, billing, or inventory transactions.

Distribution is ordinary APK file sharing through messaging, file transfer, or similar channels. No hosted download link or online release service is required. Users manually install shared updates; updates must retain the package name and signing identity. Telegram private group and one bot hold the shared encrypted snapshot. Offline viewing and local admin editing work. No server or LAN transport in v1.

Use 1–5 sections, initially one starter section. Preserve independent medication statuses for each section.

## 3. Access model and device lifecycle

Reader is the default after importing a connection file. Reader can browse, search, filter, refresh, and explicitly import replacement connection credentials for the same pharmacy as described in section 12. This connection-only action never grants admin authorization. Admin mode enables catalog/availability editing, history, imports/exports, backup/restore, connection issuance, and credential maintenance, subject to the unsupported-version restrictions in section 10.

Readers have no PIN or app lock. One-time promotion of a reader phone to admin uses a pharmacy-wide numeric PIN of at least four digits and a salted PBKDF2-HMAC-SHA256 verifier, 200,000 iterations. Store the verifier in shared pharmacy metadata; never store the PIN. Reader must first sync the verifier. Failed promotion and current-PIN change attempts share a protected local increasing delay based on elapsed time, independent of wall-clock adjustments. Preserve it across process restarts; after reboot conservatively restart the outstanding delay. Reset delay after successful verification. This slows casual attempts, not offline guessing.

Admin authorization is device-local and persists across ordinary restarts and backgrounding. An admin phone opens directly with browsing and editing available, without repeated PIN, biometric, or device-credential prompts. There is no routine switch to Reader mode or Lock admin mode action. Authorization ends on leaving or restore; observing a changed shared admin PIN verifier also requires reauthorization as described in section 12, except for the initiating phone after its own PIN change is verified as published. Setup creator starts as admin. Request an editor display name at first admin use; a local random device ID identifies this installation. Names are attribution, not authenticated identity.

This is a trusted-user model: all connected devices have the same bot credentials and snapshot key. Reader/admin restrictions are enforced in UI and domain commands, not by Telegram. Readers with technical access can extract credentials, inspect shared metadata/verifiers, and forge writes. Do not claim cryptographically enforced reader permissions or confidential shared metadata. If either is required, stop and redesign credential separation.

Leave pharmacy clears app-owned pharmacy data, pending edits, keys, credentials, cached import copies, and its pharmacy-scoped selected-section preference. It cannot erase the user's original externally shared files. Warn about pending edits on any device; require typed pharmacy name for an admin. Reader may leave after confirmation. Explain that Telegram data and externally exported files remain.

## 5. Local storage and persistent admin authorization

Room + SQLCipher holds pharmacy data; random database key is wrapped with Android Keystore AES-GCM. Keep credentials behind a SecureStore abstraction using Keystore-protected encrypted storage. DataStore stores non-secret preferences only. Exclude secrets, database, and key blobs from platform automatic backup; use explicit encrypted backups.

Persistent authorization follows section 3: no routine lock/session timeout or repeated unlock, current PIN required for PIN changes, and no restored admin authorization.

Keep the catalog database Keystore wrapper available without user authentication. Persist device-local admin authorization in protected app storage and enforce it in domain commands as well as UI. Keystore invalidation shows a recovery flow, never a silent wipe.

Screenshots are allowed. Keep secrets out of APKs, logs, crash reports, clipboard diagnostics and error URLs; section 11 specifies backup exclusions.

## 6. File formats

Connection `.aqz` and backup `.aqbak` use versioned encrypted JSON envelopes:

`v, kdf, iter, salt, nonce, ct, tag`.

v1: PBKDF2-HMAC-SHA256, 200,000 iterations; random 16-byte salt; AES-256-GCM; random 12-byte nonce; separate 16-byte authentication tag; standard Base64 for binary values. AES key is 32 bytes. AAD is UTF-8 `aqz:v1` or `aqbak:v1` followed by raw salt then raw nonce. Snapshot encryption uses the shared random 32-byte snapshot key directly. Its exact envelope is `v, nonce, ct, tag`, with integer `v=1`, standard Base64 binary fields, a fresh random 12-byte nonce, and a separate 16-byte tag; it has no salt or KDF fields. Snapshot AAD is UTF-8 `aqsnapshot:v1` followed by the raw nonce. Its encrypted JSON payload includes a stable `compatibility` object containing `schemaVersion`, `minVersionCode`, and `keyVersion`; authenticate before trusting these fields. Reject duplicate JSON keys and malformed or missing required fields. Before M3 implementation, document example envelopes and fixed crypto test vectors for all three domains, including cross-domain rejection.

Validate version, fixed v1 KDF settings, lengths and payload structure; never accept unbounded attacker-provided iterations. Complete encrypted input/output envelopes, including Base64 overhead, are capped at 10 MiB for connections/snapshots and **64 MiB (67,108,864 bytes)** for backups. Enforce actual bytes even with unknown/inaccurate stream lengths; reject oversized input/output with a clear error. History-heavy M7 backups use that same separate cap and the [bounded-resource safeguards](crypto/FORMATS.md); never report an export successful if its v1 reader cannot accept it. Wrong password/authenticated corruption share “Incorrect password or damaged file”; unsupported format is distinguished before decryption.

`.aqz` payload: schemaVersion, pharmacyId (UUID), pharmacyName, botToken, groupId (64-bit), snapshotKey (32 bytes), keyVersion, createdAt, createdBy. No role, admin PIN, backup passphrase, device identity, or unlocked state. Ask for a new file password at issuance; do not retain plaintext passwords. Minimum four numeric digits; accept Arabic digits and normalize to ASCII. Explain that short numeric passwords have limited resistance to offline guessing.

Backup passphrase: free text, at least eight characters; do not trim or silently normalize it. Never store it. Include payload schema and export timestamp.

Changing the file password re-encrypts newly issued files only; existing devices and old credentials remain usable. Actual lockout requires Telegram token revocation plus a new snapshot key. See section 12.

## 7. Data model and invariants

All shared entities have stable UUIDs. Timestamps are UTC instants; business dates are Gregorian LocalDate. Pharmacy timezone defines “today,” including exports. Local display preferences never change shared dates.

Shared records:

- Pharmacy: pharmacyId, name, timezone, schemaVersion, adminPinVerifier (salt/iterations/hash), minimum supported app version, keyVersion.
- Category/Form: id, nameAr, nameEn?, orderIndex, isSystem.
- Section: id, nameAr, nameEn?, orderIndex, isActive.
- Medication: id, nameAr?, nameEn?, genericAr?, genericEn? (at least one scientific name required), brand?, formId, categoryId, strength, note?, expiryDate?, expirySoonThresholdDays (default 60), createdAt, updatedAt, updatedBy.
- Availability: unique (medicationId, sectionId), status AVAILABLE/LOW/OUT/UNKNOWN, updatedAt, updatedBy.
- Tombstone: entityType, entityId, deletedAt, operationId. Retain for v1 at this scale; these are synchronization records, not visible catalog items.

Local-only records:

- HistoryEntry: id, operationId?, entityType, entityId, entityName, field, oldValue, newValue, editorId?, editorName?, editedAt, observedAt?, publishedRevision?. Remote observations may have unknown original attribution and use a separate observation time.

- DeviceIdentity: installation UUID, displayName, adminMode, createdAt, lastSeenAt.
- ConnectionSecrets: botToken, groupId, snapshotKey, keyVersion.
- SnapshotState: confirmed snapshot/base, authenticated publishedAt?, revision, publishId, pinnedMessageId, documentFileId, documentFileUniqueId, lastSuccessfulSyncAt, and separately retained authenticated compatibility requirements that currently restrict this installation.
- PendingOperation: UUID, transactionId, target entity/field, base value, intended value, author/time, basePublishId.
- PublishAttempt: stable publishId, retained base payload, candidate payload, included operation IDs, transport progress including uploaded file/message IDs.

Maintain confirmed shared state separately from pending edits. Visible admin data is confirmed state plus pending edits, clearly labeled when unpublished. Reader devices display confirmed state only. Admin devices do not routinely switch roles. Remote refresh must not erase pending changes.

System category Uncategorized and form Other have fixed IDs, localized names, and cannot be renamed/deleted. Categories initially contain only Uncategorized. Do not offer or seed any other starter categories; admins create their own. Seed 15 forms: Tablet, Capsule, Syrup, Suspension, Injection, Drops, Cream, Ointment, Suppository, Inhaler, Patch, Sachet, Spray, Gel, Other.

Names are trimmed and required when specified. Medication nameAr/nameEn are optional commercial names; genericAr/genericEn are scientific names, with at least one nonblank scientific name required. Blank optional names are null; strength remains required text. The scientific identity leads throughout browsing, editing, history, conflict review and reports, followed by strength/form and optional commercial names. Apply this invariant consistently to commands, CSV import, snapshots and backups; never fabricate a missing name or translation. Taxonomy/section names must be unique under the existing name normalization within their type; the expanded search-only rule for standalone ء does not change uniqueness. Manual editing and CSV share duplicate identity: overlapping normalized scientific/commercial names, the same form ID, and a strength key that normalizes digits, ignores whitespace and case, and never converts units. Thus `500mg`, `500 mg`, and `٥٠٠ mg` match, while different strengths/forms remain distinct. Warn and require explicit continuation for exact duplicates; never merge IDs silently. New saves normalize strength digits and collapse whitespace without rewriting existing catalogs in bulk.

The fresh initial contract is Room version 1 and snapshot/backup payload schema 1, without price/currency in models, storage, wire, CSV headers/clearing, reports or validation. Prior development upgrade code/exports are removed; earlier installations/files have no upgrade/import guarantee. Never delete installed databases/keys, enable destructive fallback or change app version/counters as part of this reset. Generated-export/delivery evidence belongs in validation.

Deleting category/form atomically reassigns linked medications to its fallback, records per-medication changes plus one deletion summary, and writes a tombstone. Medication delete removes visible medication and availability, preserves history and tombstone. Section delete cascades availability, requires typed name, and cannot remove the final section. Deactivation preserves availability; all sections may be inactive with an explicit closed-sections state.

Creation atomically initializes explicit AVAILABLE pairs in every existing section with history/pending work. Editing existing medications preserves availability; missing legacy or later-added-section pairs remain UNKNOWN, distinct from OUT. UNKNOWN remains readable and compatible with CSV/wire/backup, but manual single/form/bulk editors offer only AVAILABLE/LOW/OUT and never silently convert old values. New Add/Edit drafts and blank/omitted-form CSV creates use seeded Tablets by ID, falling back to Other if absent; existing forms, restored drafts and explicit CSV choices retain their values.

## 8. Sync and publishing

### Transport contract

Dedicated private group, one stable bot-owned pinned document message. Reserve its pin for Aqaqeer; unrelated/missing pins are detected as invalid. Caption is a discovery hint containing app marker, revision, publishId, and time. Authenticated payload is authoritative; caption/payload disagreement is an error, never a reason to accept data blindly.

Telegram operations: getMe, getChat, getFile, sendDocument, editMessageMedia, pinChatMessage; setup-only getUpdates/getWebhookInfo. Verify permissions during setup. Do not use getUpdates as a publish lock or replicated history feed. Do not post human publication notices or change summaries in v1. Candidate document uploads still create transport messages; these are not announcements and may remain for manual cleanup.

Snapshot: stable v1 compatibility header plus revision, publishId, parentPublishId, basedOnRevision, publishedAt, publishedBy, pharmacy metadata, entities and tombstones. History is device-local and excluded entirely from shared snapshots. No connection credentials, device unlocked state, or plaintext passwords in snapshot.

UUIDs identify publications; they do not establish causal ordering. Parent identity detects competing publications. Do not resolve a divergent branch by trusting device clock or UUID order.

### Read

Refresh on eligible foreground entry and pull-to-refresh, coalescing duplicate requests. Automatic foreground refresh skips offline/admin-busy/publishing states and a successful sync less than five minutes old; missing/future sync times do not satisfy this age guard. Manual refresh bypasses the age guard, respects offline/busy/server-cooldown guards, and reports updated/already-current results. Cache validated bot identity in process memory by token digest, retain both pin checks, and respect Telegram read retry_after without automatic write replay. Fetch pinned message and compare its document file identity and caption publication marker with the last validated snapshot; a stable pinned message ID alone never proves the document is unchanged. Download when the document identity or publication marker changes, and always download during publication verification or recovery. Authenticate, validate pharmacy/schema/references, then apply confirmed state atomically. Preserve device-local history and rebase pending edits. Record locally observed remote field changes when refreshing, without reconstructing unseen intermediate changes or importing another device’s history. A failed download/decrypt/validation leaves the previous usable state intact.

Always show last successful refresh time and publication time separately. A successful refresh of an unchanged valid snapshot updates last successful refresh time. Show an offline/saved-data indicator when validated connectivity is absent, and an amber warning when the last successful refresh is at least 24 hours old. A missing refresh says never refreshed; a future timestamp is not stale. Publication time remains distinct and never substitutes for refresh time. Refresh failures retain explicit errors. If no cache exists, show an empty offline/error screen rather than a fictitious empty pharmacy. Missing/unrelated pin shows “Snapshot unavailable — contact admin”; admins get an explicit republish/recovery action. Never automatically replace missing Telegram data with stale local state.

Reject unexplained lower revisions and same-revision/different-publication branches into an admin recovery path; preserve both local and incoming candidate data. A snapshot with a different pharmacyId is always rejected. An authenticated snapshot for this pharmacy that requires a higher minVersionCode or unsupported schema activates the persistent viewing/recovery-only state in section 10; retain the last usable confirmed data and pending edits without applying the incompatible payload. Unauthenticated, damaged, or wrong-pharmacy data must not activate that restriction.

### Merge before publish

Every normal explicit or automatic publish fetches the current valid remote snapshot first. First publication and staged credential rotation use the explicit paths below. Compare the saved base, local operations, and current remote values:

- Remote equals base: apply local change.
- Local equals remote: mark the operation satisfied without duplicate history.
- Changes affect different fields/entities: combine automatically.
- Both change the same field differently: ask with base/mine/theirs; never use last-device-timestamp wins.
- Remote deletion versus local edit: offer discard or explicit restoration after review; never silently resurrect.
- Local deletion versus remote edit: pause and show changes since the saved base; offer explicit confirmation of deletion or keeping the updated remote entity. Never let deletion silently win. Apply this rule to medications, sections, categories, and forms, including changes to linked records affected by cascade or reassignment. Confirming deletion recomputes its dependent changes against the reviewed live state and validates them as one transaction; keeping the entity cancels the pending deletion and its derived cascade/reassignment operations without erasing local history. Recheck if remote state changes again before publication.
- Validate references, unique names, section limits, and dependent changes after merging. Treat delete/reassignment as one transaction.

For repeated unpublished edits to the same field, merge the final intended value against the original confirmed base, preserving every actual edit in local history. Returning to the base value removes the net pending field change without deleting history. Preserve transaction dependencies; do not collapse edits across an in-flight publish boundary. Derived `updatedAt`/`updatedBy` fields do not independently cause merge conflicts; derive them from the accepted changes using a documented deterministic rule, never using them to choose a conflicting business value.

Present unresolved choices per medication/entity with field details. Cancel preserves edits. If remote changes again before publishing, repeat comparison.

### Publish and retry

Manual Publish is available when compatibility permits it. Edits saved while already online wait for the admin to tap Publish; saving alone does not trigger publication. Saved edits queue locally and automatically attempt publication when connectivity returns while the app is active and the device has admin authorization. A normal foreground refresh without a connectivity recovery does not publish online-saved edits. Refresh and merge first. Pause for unresolved conflicts, missing authorization, unsupported app/schema requirements, restore review, or credential maintenance; never choose a conflicting value silently. If the OS has stopped/backgrounded the app, resume a deferred reconnect-triggered publication on the next foreground opportunity rather than promising immediate background publication. Clearly indicate that queued changes may be shared automatically after reconnection. Serialize publishes within a device and capture a fixed set of operation IDs; edits made during an upload remain pending for the next publish trigger.

The Home pending-changes banner specified in section 9 exposes Review and the existing explicit Publish action. It reflects publishing, blocked/conflict, retry, and uncertain-outcome states without changing the publication triggers above. Do not clear included changes or announce success in the banner until verified read-back or normal attempt reconciliation acknowledges them; edits outside that acknowledged attempt remain pending.

First publication is an explicit bootstrap path: validate Telegram setup, verify there is no existing Aqaqeer snapshot or unrelated pin to overwrite, use revision=1, parentPublishId=null, and basedOnRevision=0, then upload, recheck the pin, pin, and verify. A newly appearing pin pauses bootstrap for review. An existing snapshot enters normal merge or explicit recovery; never treat a missing snapshot after prior publication as a fresh pharmacy.

1. Refresh, merge, resolve conflicts, and validate.
2. Persist a candidate and stable publishId, parent=current publishId, revision=current revision+1.
3. Upload encrypted candidate as a document; retain its file ID and message ID.
4. Re-read the pin. If parent changed, stop/rebase rather than overwrite knowingly.
5. Existing stable message: `editMessageMedia` to the candidate file ID with its new caption. First publication/recovery: pin the uploaded document after explicit confirmation where needed.
6. Read back and verify the expected publishId and authenticated payload. Only then acknowledge included operations and history revisions locally.
7. Do not post a separate publication announcement. Unused upload messages may remain for manual cleanup.

On timeout/termination, retain PublishAttempt and inspect remote identity before retrying. If the candidate is already current, acknowledge it. If the exact candidate is no longer current, compare retained candidate/base data and intended changes with live state to determine which operations are already satisfied; do not rely on shared history or a permanent remote operation log. Otherwise rebase the original pending operations and ask when outcome is ambiguous; never blindly replay an overwrite. Respect Telegram retry_after, use bounded exponential backoff for transient failures, and stop automatic attempts on invalid credentials/permissions. No infinite foreground spinner.

**Limit:** another device can write between the last check and media edit, or after read-back. This protocol cannot guarantee zero lost updates under overlapping publishes. Keep candidate uploads and retained local state for recovery; do not market it as a distributed lock. Guaranteed concurrent writes require a different coordinator.
