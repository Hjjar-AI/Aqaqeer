# GitHub CI free-tier controls

[Build instructions](build.md#manual-quality-and-security-workflows) own workflow commands; [validation](validation.md#ci-downloads-without-a-payment-method--2026-11-13) owns executed evidence. These controls support development/testing of this repository under [GitHub's Actions terms](https://docs.github.com/en/site-policy/github-terms/github-terms-for-additional-products-and-features#actions). They are not a certification of account billing or all repository contents.

## Automatic controls

- Every job skips private repositories and uses standard `ubuntu-24.04`, which is [free for public repositories](https://docs.github.com/en/billing/concepts/product-billing/github-actions). No paid larger runner, remote device service or paid security AI feature is enabled.
- All eleven workflows retain manual dispatch, bounded job timeouts and non-cancelling concurrency groups. Cleanup alone also runs daily at 03:23 UTC (06:23 Asia/Damascus), deleting completed runs older than seven days. Workflow 06 selects standard/demo/both; both uses independent serialized jobs, each packaging only its selected flavor. Workflow 11 reserves a production code with a durable tag, builds the standard release without signing secrets, and signs/publishes from the default branch using the release-signing environment; only reservation and publication have contents-write. Signing keys are never cached or uploaded as artifacts. Workflow 10 separately publishes selected debug APKs as a regular release, prerelease or draft after all selected builds succeed; only its publisher has `contents: write` and `actions: read`. Release assets outlive Actions artifact/run retention. Emulator API 29/35 entries run one at a time. Dependabot separately proposes weekly action and Gradle updates; nothing auto-merges; checks/builds/emulator/release verification have no unattended schedule.
- APKs, diagnostics, screenshots and videos upload automatically when their producing steps reach the upload condition. No repository-variable switch is required. Uploads can fail at GitHub's storage quota; command logs and summaries remain available even if an artifact could not upload.
- Artifacts expire after one day. UI recordings are bounded to 45 seconds per case at 360×640/1 Mbit/s. Four UI invocations per API produce at most approximately 23 MB of encoded video per API, plus PNGs/logs/container overhead; this is an estimate, not an account-wide storage cap.
- Gradle uses setup-gradle's `basic` GitHub cache provider. Runs on the default branch can save downloaded dependencies and wrapper distributions; other branches can restore caches but cannot save them. The pinned basic provider requires an exact build-script/wrapper/catalog hash and does not use older-key fallbacks; Gradle/dependency configuration updates can miss and download again. Kotlin-source-only changes retain the key. Both downloaded dependencies and wrapper distributions are included; a cache miss still permits normal downloads. Cache entries can overlap and be evicted; enabled caching does not guarantee a download-free run. No AVD cache is uploaded and no account/repository cache allowance is increased. GitHub currently includes a separate 10 GB cache allowance per repository; [billing documentation](https://docs.github.com/en/billing/concepts/product-billing/github-actions) and account settings remain authoritative.
- Cleanup can only run from the default branch, checks that condition again before API access, and checks out its script from that branch. Its write permission is confined to the cleanup job. The user explicitly chose deleting all completed workflow runs with their attempts, logs, summaries and attached artifacts, including workflow APK downloads; this supersedes the earlier run/APK-preservation policy. Scheduled retention is seven days across all workflows, including Dependabot. The manual button defaults to preview and seven days; choose `older_than_days=0` and `dry_run=false` for an immediate clear of completed runs. Active/current runs are excluded. Repository/run ownership, age, attempt and updated time are rechecked; pagination finishes before deletion and absence is verified using bounded GET-only polling (six observations, 31 seconds of backoff). Unconfirmed deletions remain failures while independent eligible runs continue; DELETE is not retried during confirmation. GitHub Releases/assets, repository files and caches are untouched. Copy selected debug APKs to a Release or download them before clearing their runs if they must survive. Deleting logs does not reclaim artifact allowance; artifact/run deletion may remove retained downloads.
- [Repository policy checks](../.github/scripts/check-ci-policy.py) parse both workflow extensions and referenced local composite actions, reject duplicate keys, preserve the `on` key, and enforce triggers, runners, pins, permissions, concurrency, upload retention, cache settings and cleanup guards. Named and unnamed steps receive the same checks. [PyYAML](../.github/requirements-ci.txt) is version/checksum-pinned for Ubuntu's Python 3.12 x86_64 wheel. Actionlint separately validates workflow syntax/expressions through a shared checksum-verified installer. These checks cannot control GitHub billing/settings or prevent a repository writer from changing the policy itself.

## Owner account checks

The owner confirmed there is no payment method saved and none will be added. GitHub [blocks quota-limited usage when no valid payment method is on file](https://docs.github.com/en/billing/concepts/product-billing/github-actions#managing-your-budget-for-github-actions). Standard public-repository runners remain free; storage limits may block an artifact upload without stopping unrelated checks. This implementation relies on the owner's account statement; it did not independently inspect billing settings.

1. No `CI_UPLOAD_ARTIFACTS` variable or paid plan is needed. Publish the workflows and run the desired manual check; download APK/PNG/MP4/report artifacts within one day if the upload succeeds.
2. Keep the repository public and keep using the pinned standard runners. Existing private-repository guards prevent these jobs from starting if visibility changes.
3. Monitor artifact and cache storage separately and optionally enable included-usage alerts under account **Settings → Billing and licensing → Budgets and alerts**. If an upload hits quota, inspect unexpired artifacts; one-day artifact expiry usually precedes the scheduled seven-day run deletion. Run cleanup removes attached APK downloads too; Release assets are preserved. Never increase the cache allowance to bypass eviction.
4. If a payment method is ever added, first review an **Actions $0 budget with “Stop usage when budget limit is reached”** where offered. Alerts alone do not stop spending. [Budget setup](https://docs.github.com/en/billing/how-tos/set-up-budgets), [budget behavior and limits](https://docs.github.com/en/billing/concepts/budgets-and-alerts).
5. Run **01 - Checks - Repository integrity** after workflow changes. Use **09 - Maintenance - Clear workflow runs and logs** with `dry_run=true` to preview a manual clear; its daily seven-day deletion is automatic. A configured check is not an executed pass.

No billing settings, variables, spending limits or security settings were changed. Existing usage and accrued storage are not erased by cleanup; account-wide billing remains controlled by GitHub account settings.

## Dependency advisory review

**02 - Checks - Dependency vulnerabilities** resolves app runtime classpaths (including test runtime classpaths), resolvable KSP configurations and project buildscript classpaths using the pinned wrapper and [inventory init script](../.github/dependency-inventory.init.gradle). It compiles/packages nothing and does not reserve a version or write lockfiles. Configuration provenance is retained; unresolved dependencies or empty processor/build-plugin inventories fail rather than claim complete coverage. The November 13 hosted baseline resolved 341 coordinates, including processor/buildscript scopes. The patched graph still needs fresh authorized resolution.

Only resolved public Maven group/artifact/version coordinates are sent to the public [OSV batch API](https://google.github.io/osv.dev/post-v1-querybatch/); no credentials or app data are sent. The helper follows pagination and fails incomplete requests. Raw findings remain in `findings.json`; `triage.json` separates active and excepted matches. Unexcepted advisories fail without changing dependency pins. Embedded native component versions, non-Maven build tooling and unknown vulnerabilities remain outside this scan.

[OSV exceptions](../.github/osv-exceptions.json) remain empty. The reviewed remediation pins KGP/Compose/serialization to 2.4.20 and KSP to 2.3.12, with minimum buildscript constraints for Guava 33.7.2-jre, Commons Lang 3.18.0, jose4j 0.9.6, aligned Bouncy Castle 1.85 modules and JDOM 2.0.6.1. A separate `ksp` constraint covers processor Guava. These candidates exist in Maven Central and returned no OSV matches on November 13; that coordinate check is not a fresh resolved graph, compatibility or compilation pass. The KGP override retains AGP built-in Kotlin and KSP’s global-configuration compatibility flag preserves existing processors. Constraints permit higher selected versions; scanner findings remain visible rather than suppressed. Each entry requires exactly `id`, `coordinate` (`group:artifact:version`), `reason` and `expires` (`YYYY-MM-DD`, exclusive UTC expiry). Duplicate, malformed or expired entries fail, even when the corresponding dependency is absent. Scope exceptions to a reviewed exact version; they suppress matching advisory failures while retaining the finding, reason and expiry in diagnostics.

The manual security workflow has separate Java/Kotlin, Python and Actions CodeQL entries. Java/Kotlin retains both production flavors with forced compilation; Python and Actions use no-build analysis. Java/Kotlin and Python use `security-extended`; Actions uses its default suite. Each language has a distinct result category and artifact. A successful analysis/upload is not proof of zero security findings.

## Emulator presentation and assertion evidence

The emulator is configured for six method invocations on each of API 29 and API 35: the existing demo details check, LIGHT/DARK/AMOLED large-Arabic/recreation checks, and two public-envelope checks. The presentation method asserts Arabic locale, RTL configuration, active 1.3× font scale, persisted theme/native window background, reachable scientific medication details, read-only controls and restored navigation. These assertions remain unverified until hosted execution; they do not establish complete layout/contrast/TalkBack acceptance. Successful runs should provide detail/Home screenshots for human review.

[CI capture rules](../app/src/androidTest/kotlin/com/aqaqeer/app/CiFailureCaptureRule.kt) catch selected UI failures inside the Compose activity lifetime; the new presentation test additionally captures before its preference cleanup. PNGs are pulled alongside host fallback screenshots, transcripts, per-case status and APK/device provenance. Test setup failures/process crashes/timeouts can bypass assertion capture, so post-instrumentation fallback and bounded logcat remain. Missing expected success PNGs or capture failures fail the helper. Physical phones, live Telegram and migration tests remain excluded; existing instrumentation sources still need to compile before selected methods can run.

## Release output and signing limits

**08 - Verify - Release output** uses wrapper `:app:assembleStandardRelease` with normal checkout-local numbering and Desktop exports disabled. It requires R8 mapping/resource-shrinker evidence, inspects required code/resource/license entries and forbidden verification files, checks package/debuggable/minimum/target SDK, ZIP alignment, native ABI/ELF machine and 64-bit 16 KB load alignment. `apkanalyzer manifest print` inspects the packaged manifest: requested permissions must be INTERNET and ACCESS_NETWORK_STATE, plus only the optional app-scoped AndroidX receiver permission with a signature-only declaration. Backup and cleartext traffic must both be explicitly disabled. Diagnostics and the unsigned-labelled inspected APK are separate artifacts; cleanup preserves the APK artifact.

No signing key is supplied or created. An unsigned output is explicitly reported as **not ready to distribute**, even if structural checks pass. To establish update continuity, manually sign with the original private release key and verify its certificate; never substitute a fresh key for an installed app. Optional **Run workflow** input `expected_certificate_sha256` defines the expected original certificate: any signed output must match it, and supplying it with an unsigned output fails identity verification. Signing material remains outside this repository; the workflow does not configure signing or claim installation/runtime acceptance.

## Repository integrity and secret checks

**01 - Checks - Repository integrity** validates local Markdown file/heading links (excluding fenced examples and ignored historical evidence), JSON/TOML/XML/Python syntax, workflow syntax/action pins and CI policy. The credential check scans current tracked UTF-8 text for selected private-key, GitHub-token, Telegram-token, AWS-access-key, OpenAI-key, Google API-key and Slack-token formats. Recognizable private signing/credential filenames are rejected without reading their contents. Reports include file/line/category only; values and credential hashes are never printed. It is not a full secret/history scan and cannot detect arbitrary passwords. Machine-private paths, migration contents and generated schemas are excluded.

For broader prevention, review GitHub's repository **Settings → security** options for secret scanning/push protection and enable the features [available free for public repositories](https://docs.github.com/en/code-security/how-tos/secure-your-secrets/detect-secret-leaks/enable-secret-scanning), including [push protection](https://docs.github.com/en/code-security/how-tos/secure-your-secrets/prevent-future-leaks/enable-push-protection). Do not purchase an Advanced Security plan or enable paid AI features for these workflows. A reported public fixture should be verified before any narrowly scoped exception; do not weaken checks to hide a real credential.
